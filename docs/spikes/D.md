# Spike D: what existing open simulators can teach us

Ticket S-006. Question: should `sdsim` keep "build our own engine" (OD-7, ADR 0003 decisions 1, 2 and 4), and which ideas are worth borrowing from **Breakscale** and **loadsketch**. Ideas only, no code (PLAN S-006).

## Against the three ADR 0003 decisions

**#1 Component-first registry, catalog generated from descriptors: supported by the evidence.** Neither project has one. Breakscale comes closest: a registry of behaviour objects keyed by a closed union, read once at build time into a direct reference on the node (kind-agnostic event loop). But a new kind still means editing the union and writing a behaviour object inside the package, and nothing outside it can register. An unknown kind also degrades silently to plain-server semantics (`behaviourFor`: "so a topology saved by a newer build still loads"), the opposite of our `not-modeled` rule. loadsketch is the clearest argument for the decision: a component touches about ten files in a twelve-step list (`kinds.ts`, `design.ts`, two `switch` statements and a plan builder in `sim.ts`, `scale.ts`, `cost.ts`, `constraints.ts`, `paramLayout.ts`, `ui.ts`, `ComponentNode.tsx`, `en.ts`), and a script (`check-agents-md.ts`) exists to keep that list true. Our reuse gate G4 (a component written outside the packages) has no counterpart in either.

**#2 Components as generator processes: no evidence against; the one example I gave was wrong.** Neither project writes components as generators. Breakscale does use generators for drivers: the "break it" search (`verify.ts` `searchSteps`, `breakitJob.ts`: "plain data in, a generator out; the worker and the main-thread fallback both step the same generator") and the judge's `playRun`, a precedent for resumable, sliceable runs that S-020 can use. Its components are callback hooks: a closed set of return types (`AdmitAction`: shed, serve, passthru, handled; `RouteMode`: all, one, none; `CompleteAction`: downstream, complete; `PumpMode`) over about twenty optional hooks (`onAdmit`, `route`, `pickEdge`, `onServiceComplete`, `onTick`, `initState`, `onDownstreamResult`, `onWake`, ...). That hook set does express 33 kinds, including a token bucket (`ratelimiter`, `behaviour-edge.ts`) built on `onAdmit` with a lazily computed refill from `now - lastRefillMs`: no refill process, and its header says why (the engine advances by frames, so anything that decides "has enough time passed" must compare simulated timestamps or the same seed gives different runs at different frame rates). So it is the callback-style fallback ADR 0003 #2 already names ("state machines behind the same descriptor"), shown to work at scale. Spike A measured our generator path (about 2.7 M events/s in a model against 3.0 for callbacks); the decision stays.

**#4 Request moves `reply`, `call`, `handoff` with topology deciding neighbours: consistent with both, thinly evidenced.** The two facts below support ADR 0003 #3 and the `call` move, not the three moves as a set; the nearest analogue of `handoff` is Breakscale's `acksBeforeDone` for retry queues and write-behind ("answer the caller, then pass a copy on") and `AdmitAction: 'handled'`. Both let a request carry its key to every downstream node (Breakscale: `ReqLike.key`, "inherited unchanged by every downstream call", the same reason as ADR 0003 #3). Both model a thread-per-request server that keeps its slot while it waits for its downstream (Breakscale: `blocksOnDownstream`; loadsketch: "blocking model"). Breakscale routes by `RouteMode` and a node's edges, not by an explicit route field, like our decision.

**Build or adopt (OD-7): the evidence does not argue for adopting.** Both are MIT and TypeScript and run in a browser worker, so a fork is possible; the strongest alternative is "fork one and trim to client, api-server, cache, db". Against it: (a) neither has per-component honesty labels with evidence ids, the contract descriptors, or open registration, which are the requirements of ADR 0003 #1 and PLAN 9.3; (b) both engines are separable and headless (Breakscale's MCP server imports its engine without a UI; loadsketch has a `src/core` entry point, a boundary test and a CLI), so a fork is cheaper than it first looks, but it would be a fork of a 200 KB engine of 33 kinds, written to their UI and content assumptions, kept in step with a fast-moving upstream for a small subset of it; (c) our determinism requirement (the same event-log hash on Node and Chromium) would need to be re-proven on their code: Breakscale has portable math, loadsketch calls the platform's `Math.log`, `cos` and `pow`; (d) what the fork would save is the first two or three engine tickets, and spike A shows the kernel and oracles exist already. This is a recommendation for SG0, not a decision: OD-7 stays with the owner, and the caveat that I did not run either engine applies.

## Ideas worth borrowing

| Idea | Where it comes from | What we do with it |
| --- | --- | --- |
| **Deterministic math is a real cross-platform problem.** Breakscale ports V8's fdlibm because, per its header comment, `Math.log` differs on Apple silicon (arm64 fuses multiply-adds in V8's C++ copy; about 2 in 100 uniform draws differ in the last bit) and Safari calls the platform libm (about 1 in 12). These are the author's claims, not measured here, and the mechanism differs from spike A's (a V8-version difference between Node 24.22 and Chromium 159 on one machine) | `src/sim/fdlibm.ts` header | Consistent with spike A on the point that matters: do not trust `Math.*` for replay. Our `rng/log.ts` uses only JavaScript arithmetic, which ECMAScript does not let an engine fuse, so it should be stable on arm64, but that is **untested**: add an arm64 and Safari run to the V9 check (S-091). The S-022 gamma service (cv other than 1) needs more than a log: use the polar method for normal draws (log and sqrt, no trigonometry; both projects use Box-Muller with `cos`); for shape below 1 both boost with `pow(u, 1/shape)`, which needs a deterministic `exp` or `pow` (the reason Breakscale ported both); and the acceptance step takes `log(v)` with `v` above 1, outside the domain `[2^-1022, 1]` of our `deterministicLog`, so extend the domain or use `-log(1/v)` |
| **A generated accuracy page with a "known deviation" row** | `docs/accuracy.md`, `scripts/accuracy.ts` | The validation suite (S-040) emits `docs/accuracy.md` from the oracle cases, deviations included; it becomes the evidence behind the `modeled` labels and a source for the limitations page (S-043) |
| **Metric definitions stated exactly (five rules):** warm-up excluded; the summary follows every request sent in the measured window until it ends; the time series counts by completion time; unfinished work is counted separately; percentiles from a log-bucketed histogram with error below 0.5% | `docs/model.en.md` section 6 | Adopt these five rules in `docs/model/metrics.md` when S-021 is claimed (MP 4.5 is not readable here; check it says the same) |
| **A callee does not know that its caller gave up; its work is wasted** (no deadline propagation by default; "as in most real systems" is the project's own unsourced claim) | `docs/model.en.md` section 5; Breakscale's retry-storm example | State it in `docs/model/api-server.md` and cover it with a V4 retry-amplification test (S-023b, S-041); that test needs a published source for the claim (golden rule 2). Breakscale's retry-storm test also reports a stochastic onset (failure rates from 40% to 95% across seeds): a V4 retry-storm lab should show that spread, not hide it |
| **Captions by simulated time, and a note that the model compresses time** | Breakscale `incidents.ts`: `captions: {atMs, text}[]`, `simNote`, `story` and `source` taken only from the postmortem | Same shape as our `case.timeline` (S-103), which this independently supports; for incidents (S-090) require a `sim_note`-style field saying what the simulation changes in time and size |
| **Untrusted-input hygiene on seeds and schedules** | `seed.ts` (a seed is a uint32 or nothing), `faults.ts` (a cap of 1000 events, one validator for every entry point) | Add `maxItems` to `traffic.schedule`, `scenarios`, `case.timeline` in the schema (S-010b) and validate the seed as a uint32 in the lab runtime (S-050) |
| **Agent-facing guide generated from the catalog** | loadsketch `aiGuide.ts` to `llms.txt` and `SKILL.md` | `sdlab` agents write specs against our catalog (D5). S-010b can emit `contract/AGENT-GUIDE.md` from the descriptors, next to `catalog.json` |
| **A script that checks AGENTS.md** (every path exists, every named symbol is found by a word match, every command resolves: the npm script exists, the file exists, the binary is installed; none is run) | loadsketch `scripts/check-agents-md.ts` | A small tooling ticket for this repo's AGENTS.md and `docs/` (low priority) |
| Golden-hash tests with an `UPDATE_GOLDEN=1` and a commit-message rule; a speed budget measured in CPU time (`process.cpuUsage`, Node only) | loadsketch AGENTS.md rules 2 and 5 | Golden hashes already planned (V6). CPU time suits a CI regression budget for the Node perf tests; it cannot replace the wall-clock Worker budget of A5 in PLAN 9.4 |
| **Refill and every "has enough time passed" decision from simulated timestamps, never per tick; the event log must not depend on the frame size** | Breakscale `behaviour-edge.ts` header and `refill()` | Rule for components written in S-018 (the token-bucket rate limiter, G4) and for the S-020 snapshot cadence: a run sliced into 100 ms frames must give the same event-log hash as one run |
| **Design briefs with floors:** a processing time cannot be set below the component's default, a hit ratio cannot exceed its default, a fixed node cannot be edited; "a smaller number is not an answer" | loadsketch AGENTS.md and README | The same trap as targets that reward cutting timeouts or service times: check it in the lab-CI wrong-answer checks (S-051) and in the `allowed_edits` ranges of the Unit 0 and caching specs |
| **A metric with no meaning for a kind shows nothing, never a plausible number** | Breakscale `AGENTS.md` (the readout step) | Matches our honesty labels; make it a descriptor rule in S-010b: a component lists only the metrics it emits |
| A "sim vs real" issue template for reports that the model disagrees with reality | loadsketch `.github/ISSUE_TEMPLATE/sim-vs-real.yml` | For the public beta (S-093), not now |

## Component set against our catalog (PLAN asked for this)

Both projects model client, load balancer, API server or service, cache, database (with replicas), queue and worker, rate limiter, CDN, circuit breaker and autoscaling; Breakscale also lists shards, stream brokers, WebSocket gateways, serverless functions and bulkheads; loadsketch adds DNS, a function kind and a `custom` station. Our plan covers the same ground in a different order: the beta needs only client, api-server, cache and db (S-022 to S-025a); load balancer, queue and worker, rate limiter, CDN and the breaker are S-026 to S-029; shards and quorums S-031; autoscaling, functions, brokers, gateways and bulkheads are not planned for v1 (PLAN 1.3 excludes anything outside the 16 labs). Nothing in this comparison argues for adding a component to the beta.

## What not to borrow

- One 200 KB engine file with a `switch (kind)` (loadsketch) or a closed kind union (Breakscale): the opposite of ADR 0003 #1.
- Learner text in the code (loadsketch keeps Chinese source strings in `t('...')` calls): against AGENTS.md's language policy.
- `scale.ts` (running 1/k of the traffic): its own accuracy page lists known deviations (cache TTL under scaling, token-bucket burst, near-saturation waits); our event budget makes it unnecessary.
- A cost model, Terraform import, price tables: non-goals (PLAN 1.3).
- Silently treating an unknown kind as a plain server (Breakscale `behaviourFor`): our rule is that `not-modeled` ids are an error.
- Per-seed single-run accuracy checks and a pinned known deviation (loadsketch): ours use ten seeds, and a known deviation is a failing or quarantined test with a ticket.
